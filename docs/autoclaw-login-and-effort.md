# AutoClaw 登录与档位：两个产品决策的记录

> 2026-10-17。本文记录两件**有取舍**的决定，供后人判断「要不要改」。
> 数值与协议事实的完整取证见 `docs/audit/pr111-autoclaw-audit.md`。

## 一、默认思考档为什么是 `high`，不是 `max`

上游（智谱 AutoClaw）的思考档词汇表有 7 档：
`off` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max`。
**我们只声明其中三档：`low` / `high` / `max`**，默认 `high`。

### 为什么只声明三档

实测（真实凭据、多次采样）表明：**同一个档位内的推理量波动跨 16 倍，
且各档区间完全重叠**。

| 档位 | 三次 `reasoning_tokens` 样本 | 中位 |
|---|---|---|
| (不发字段) | 1949 / 5509 / 11979 | 5509 |
| `low` | 3337 / 4334 / 11985 | 4334 |
| `high` | 9448 / 11985 / 5555 | 9448 |
| `max` | 609 / 8200 / 1947 | 1947 |

⇒ **无法**用数据证明相邻档位（如 `low` vs `medium`）存在可感知差异。
展示一个「实际无差别」的档位等于给用户**假选择**，所以只给差异最可能显著的
三个端点档。

⚠️ 但「三档存在」这一事实**是可靠的**：远端模型配置里每个模型都声明
`reasoningLevel: ["low","high","max"]` —— 这是上游自己的表态。
（我们无法证明的是「相邻档强度差多少」，不是「档位是否存在」。）

### 为什么默认不是 `max`

用户 2026-10-17 明确取舍：**`max` 的适用面太窄**。三条理由：

1. **`max` 太慢，日常代价过高** —— 实测在同一道需要多步推演的题上，
   单次可跑 **170~192 秒**（`max` 与 `low` 都出现过 >190s 的样本）。
   一次普通对话让用户等两三分钟是不可接受的默认行为。
2. **`high` 是官方推荐默认** —— `docs/autoclaw-models.md:72` 原文标注
   「**【官方推荐默认】** 完整展开推导演算」。
3. **`high` 是均衡位** —— 远端 `reasoningLevel` 的顺序是
   `["low","high","max"]`，`high` 居中。

⇒ `high` 是**够用且不会让用户等两分钟**的那一档，属于折中，
**不是**「已证明最强可用」。要极限推理时用户可手动选 `max`。

### ⚠️ 两个不可省的技术约束

- **数组顺序必须是强度序（弱→强）**，不能「把默认档排第一」。
  宿主把它当**展示顺序**，官方客户端直接 `map` 不排序
  （AGENTS.md 记载）⇒ 把 `high` 排首位会让横向档位轴变成「左强右弱」。
- **默认档要用具名常量表达，不得用 `efforts[0]` 反推**。
  本仓库记载过 raccoon 那处用 `array[0]` 反推、顺序一改就静默翻成最弱档，
  且该分支不可达 ⇒ 恒真断言抓不到。

两条都有守卫：`tests/unit/autoclaw.spec.ts` 的
「默认档必须是 `high`」与「默认档不是数组第一项」。

## 二、登录**不需要**读取桌面端/IDE 的用户数据

### 结论

**插件可以独立完成登录，全程不读 `%APPDATA%\AutoClaw-official\` 下的任何文件。**
只需用户提供手机号 + 收到的验证码。

### 实测证据（真实短信、真实上游）

用**自造的随机 deviceId**（`crypto.randomUUID()`，刻意不读桌面端的
`device-id.json`）走完两步：

| 步骤 | 端点 | 结果 |
|---|---|---|
| 1. 发验证码 | `POST /userapi/v1/agent-send-code` | `code:0`，手机收到短信 |
| 2. 验证码兑换 | `POST /userapi/v1/agent-login` | `code:0`，拿到 `access_token`(337 字符) + `refresh_token`(339 字符) |

兑换返回的字段全集：`user_id` / `user_name` / `first_login` /
`access_token` / `refresh_token` / `account_type`。

### 为什么自造 deviceId 可行（源码依据）

桌面端自己的实现就是
`new DeviceIdentityStore(file, createId = crypto.randomUUID)`，
`getOrCreate()` 里执行 `createId().trim()`。
⇒ **deviceId 就是随机 UUID，不含任何设备指纹**。桌面端首次启动时也只是
造一个随机值写盘。所以插件自造一个与之等价，不需要「继承」桌面端的值。

⚠️ 唯一要求：**发码与兑换必须用同一个 deviceId**
（桌面端注释：不一致服务端回 `631016`）。

### 当前代码的实际状态

`src/autoclaw-oauth.ts` 的 `resolveDeviceId()` 的查找顺序是：

1. 显式传入的 deviceId
2. `DSH_AUTOCLAW_APPDATA`（**测试隔离口**）
3. `%APPDATA%`（读桌面端的 `device-id.json`）
4. `crypto.randomUUID()`（**兜底**）

⇒ 也就是说：**桌面端装了**就复用它的设备号，**没装**就自造一个。
两条路都能登录 —— 这已经是「可脱离桌面端」的正确行为，
**不是**「必须读 IDE 数据」。

### 建议（未实施，供决策）

若希望**彻底不读桌面端**：
- 最小改动：把 `resolveDeviceId()` 的桌面端读取分支去掉，只用
  「显式传入 → 随机 UUID」，并把设备号持久化到插件自己的状态目录
  （`DSH_JET_HUB_STATE_DIR`）以便多次登录用同一个值。
- 代价：与桌面端登录会被上游视为**两台不同设备**（如果上游有设备数限制，
  可能占用额度）。**这一点未验证**，改之前应先确认上游是否有设备数上限。

⚠️ 另一个仍然依赖桌面端的入口是「一键导入本机凭据」
（`probeAutoclawLocalCredential`，读 DPAPI）—— 那是**可选**的便捷路径，
不是登录的必经之路。纯短信登录不碰它。

### ⚠️ 一个新的实测事实：普通手机号也能注册

用 130****5433 走完登录后，兑换成功但**推理返回
`402 {"message":"积分不足,请充值"}`**。
⇒ 该账号是新注册的、**没有积分**。这说明：
- 上游允许任意手机号注册登录（不需要邀请/白名单）；
- 但**新账号默认无额度**，必须靠签到或充值获得。

⚠️ 好消息是这同时验证了额度错误的归类：HTTP 402 → 我们归
`QUOTA_EXCEEDED`（字面量），文案「积分不足,请充值」会原样透出。
